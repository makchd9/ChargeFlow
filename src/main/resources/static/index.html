    The problem

    An urban charging hub has a fixed number of charging modules per connector type (CCS2, Type 2 AC, Bharat DC-001). On a busy day more vehicles arrive than the hub can fully charge. Each vehicle is parked for a known window and needs a number of 30-minute charging slots. The power cabinet can switch modules between parking bays at slot boundaries. Goal: deliver as many charging slots (kWh) as possible, protect a priority tier (emergency, fleet, low-battery, tight deadline), and explain where capacity is the bottleneck.

    Pipeline

    1. Validation (Java): plate format, duplicates, time windows, connector compatibility, hub feasibility.
    2. Bloom filter (CO5): each plate is screened against the subscriber registry. "Definitely absent" skips the database. "Possibly present" is always confirmed by an exact lookup, so false positives are caught and never trusted.
    3. Randomized Quickselect (CO5): finds the k-th highest priority score in expected O(n) to split vehicles into tiers, and gives p50/p90 statistics.
    4. Edmonds–Karp max-flow (CO4): network source → vehicle → (connector, slot) → sink. Tier-1 source arcs are added first and solved, then tier-2 arcs are added and the solver resumes. Augmenting paths never decrease tier-1 flow.
    5. Min-cut: certifies optimality and lists the binding (connector, slot) pairs.
    6. Module assignment: maps slot grants to concrete module ids, keeping a vehicle on the same module where possible.

    Honest limits

    • Max-flow maximises charging slots, not the number of fully charged vehicles. Maximising fully-served vehicles is a knapsack-like NP-hard objective. We report it, but do not claim to optimise it.
    • Charging may be split into non-contiguous slots (the power-sharing model). Requiring contiguous sessions makes the problem NP-hard (interval scheduling with demands).
    • A slot is all-or-nothing at the vehicle's effective power. Taper near 100% SoC is ignored.
